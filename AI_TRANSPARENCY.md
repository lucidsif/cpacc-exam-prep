# AI Transparency

This document explains how AI is used in this app and how to audit it. It is the long-form version of the in-app **"About AI in this app"** dialog.

## Why this document exists

Accessibility professionals — rightly — are often skeptical of AI tooling. AI can hallucinate, misrepresent sources, and produce confidently-wrong content. For a study app aimed at the **IAAP Certified Professional in Accessibility Core Competencies (CPACC)** credential, that's not a hypothetical concern: a wrong answer learned during practice can be a wrong answer on the real exam.

So every AI-generated piece of content in this app is labeled in the UI with a **provenance badge** that surfaces the same information you'd find on an [IBM AI FactSheet](https://research.ibm.com/blog/ai-factsheets) or a Model Card:

- **Source** — where the content came from
- **Generated by** — which model wrote it, when
- **Human review** — what was checked
- **Confidence** — how much you should trust it without further verification
- **Limitations** — what it can't do

## The three content buckets

The app contains three categorically different kinds of AI-touched content. Each has its own treatment.

### 1. AI-authored from a citable primary source — *high confidence*

| Where | Source | Review |
|---|---|---|
| Main practice question bank (`data/questions.js`) | IAAP CPACC BoK (Oct 2023, v4.0) — every item has a `cite: "BoK p.X"` field | Item-by-item check against the cited page |
| Laws & standards reference (`data/legal.js`) | Public records of laws, treaties, conventions, standards | Author verified year, jurisdiction, scope against authoritative sources |

These items were written by Claude with the primary source available in context, and were reviewed against the citation. The badge is **green / High confidence**.

**Caveat:** "High confidence" still means *AI-authored*. If you find a discrepancy between an item and the cited source, the source wins. Please [file an issue](#filing-a-correction).

### 2. AI-derived from author's notes — *medium confidence*

| Where | Source | Review |
|---|---|---|
| Bear-notes practice bank (`data/bear-questions.js`) | Author's Bear notes tagged `#cpacc/practice` and `#a11y/*` | Spot-checked by author |
| Bear-notes flashcards (`data/bear-flashcards.js`) | Same | Spot-checked by author |
| Human disabilities reference (`data/disabilities.js`) | Author's notes; prevalence stats cross-referenced with WHO / CDC / Epilepsy Foundation | Stats verified against external sources; descriptions paraphrased from notes |

These items were generated by Claude from a secondary source (the author's own study notes, which are themselves a distillation of various CPACC reference material). One step removed from primary sources. The badge is **amber / Medium confidence**.

**Caveat:** The author's notes can contain interpretive bias, outdated stats, or paraphrasing errors that propagate into the generated content. Treat these items as study aids — verify before relying on them in a high-stakes context.

### 3. AI live chat — *variable confidence, not pre-reviewed*

| Where | Source | Review |
|---|---|---|
| Per-question chat tutor | Live response from the operator's configured provider; receives question text, choices, correct answer, BoK rationale, and citation as context | **None** |
| Home-page tutor chat | Live response from the operator's configured provider; no question context | **None** |

The chat tutor is provider-agnostic. The operator chooses one of three backends with environment variables: **Anthropic**, **OpenAI**, or a **local** OpenAI-compatible model server they run themselves. `GET /chat-status` reports which one is active as `{ enabled, provider, model }`, so you can always check what is answering you.

Every chat response shows a permanent **amber banner** at the top of the transcript:

> 🤖 **AI live response — not pre-reviewed.** Verify against authoritative sources.

This is the bucket most likely to surprise you. Any of these models can produce plausible-sounding but incorrect statements (hallucinations), particularly on edge cases or recent regulatory changes. Quality also varies by which provider and model the operator picked: a small local model is generally weaker on CPACC specifics than a frontier cloud model. The badge is **gray / Variable confidence** because each response is unique.

## What the app is *not*

- **Not authorized or endorsed by IAAP.** This is an independent study aid.
- **Not equivalent to the actual CPACC exam.** The real exam is 100 multiple-choice questions in 2 hours (~70% to pass). This app's tests are 20-question study sessions weighted to the BoK domain mix (40/40/20).
- **Not a replacement for the official Body of Knowledge.** Use this *alongside* the BoK PDF and any accredited training material — not instead of them.
- **Not a guarantee of correctness.** Every item is fallible. The provenance badges exist so you can decide which items to trust.

## Confidence pill semantics

| Pill | Color | Glyph | Meaning |
|---|---|---|---|
| **High** | Green | ● (filled circle) | Authored from a citable primary source; author reviewed against citation |
| **Medium** | Amber | ◐ (half circle) | Derived from author's notes or secondary sources; spot-checked, not exhaustively reviewed |
| **Low** | Red | ○ (open circle) | Significant uncertainty flagged — usually paired with a visible Confidence note on the item |
| **Variable** | Gray | ? | Live AI response; quality varies per query |

The shape, color, AND label all carry the meaning (WCAG SC 1.4.1 — Use of Color). You don't need to perceive color to read confidence.

## How AI processing works for chat

When you open chat on a question and send a message:

1. Your message is sent to the **Cloudflare Pages Function** (or, in local dev, to `node server.js`) along with the current question's text, choices, correct answer, per-choice rationale, and BoK citation as additional context.
2. The endpoint forwards the request to **whichever LLM provider the operator configured**, using a server-side credential. The credential never reaches your browser.
3. The reply is normalised to `{ reply, provider, model }` and shown in the chat log. The `provider` and `model` fields tell you exactly what answered.

The home-page tutor chat (`/chat-general`) sends only the message and prior turns — no question context.

### Where your chat messages actually go

This is the part worth reading before you type anything into the tutor. It depends entirely on which provider the operator chose:

| Provider | Where your message goes |
|---|---|
| `anthropic` | Anthropic's API. Processed per [their data usage policy](https://www.anthropic.com/legal/privacy). |
| `openai` | OpenAI's API. Processed per [their privacy policy](https://openai.com/policies/privacy-policy/). |
| `local` | **Nowhere external.** The message goes to a model server the operator runs on their own machine or network. No third-party vendor receives it. |

Choosing `local` is the meaningful privacy difference: your chat messages never leave the operator's own hardware. With either cloud provider they do leave, and are subject to that vendor's retention and usage terms rather than this project's.

Two caveats on `local`: it only applies when the operator is running `node server.js` (or a local `wrangler pages dev`) themselves, since Cloudflare's edge network cannot reach a private machine; and "local to the operator" is not the same as "local to you" if you are using someone else's deploy.

Check `GET /chat-status` on any deploy to see which provider is live.

No prompts are logged or stored server-side beyond the duration of the request. Cloudflare may keep operational request logs; refer to [Cloudflare's privacy policy](https://www.cloudflare.com/privacypolicy/).

## How to audit AI provenance yourself

Every piece of content can be inspected without using the live app:

1. **Practice questions:** open `data/questions.js` or `data/bear-questions.js`. Each item lists its `cite` field (BoK page or other source) and may include a `flag` field explaining known uncertainty.
2. **Flashcards:** open `data/bear-flashcards.js`.
3. **Disabilities reference:** open `data/disabilities.js`. The `keyFacts` arrays are where most external sourcing lives (WHO, CDC, Epilepsy Foundation).
4. **Laws & standards reference:** open `data/legal.js`. Each item has `type`, `year`, `jurisdiction`, `summary`, and `keyFacts`.

The bank-level `*_PROVENANCE` constant at the top of each file states the source, generator, review process, confidence, and limitations for everything in that file.

## Filing a correction

If you find an item that's wrong:

1. **Wrong answer in a practice question:** use the [Wrong answer issue template](.github/ISSUE_TEMPLATE/wrong-answer.yml).
2. **Inaccurate stat / source / law detail:** open a bug issue and reference the data file + item id.
3. **Misleading or harmful chat response:** open a bug issue with the prompt, the reply, and the `provider` / `model` reported by `/chat-status`. We can't change the model, but we can adjust the system prompt or flag the relevant question.

Corrections are merged after a maintainer verifies against the cited authoritative source.

## What if I disagree with this app's approach to AI?

A reasonable position. Forks are welcome — the MIT license permits any modification. Common variants you might consider:

- **No AI at all** — strip the chat UI and rewrite the question banks by hand.
- **Different model or provider** — set `LLM_PROVIDER` to `anthropic`, `openai`, or `local` and `LLM_MODEL` to any model that provider serves. No code change needed.
- **Keep chat off the cloud entirely** — run `node server.js` with `LLM_PROVIDER=local` and your own model server. Chat then never leaves your network.
- **More cautious labeling** — mark all content as "Low confidence" until you've personally verified each item, then bump the per-item provenance.
- **No live chat** — remove the `functions/` directory entirely. The app works without it.
